## 4. Migration rehearsal (V1 database to V1.1)

Method: the V1 rehearsal in `docs/MIGRATION_REHEARSAL.md`, repeated for this step. The existing `scripts/migration-rehearsal.ts` is built for a V0 tree (the `pre-makeover` tag) and a 34-migration upgrade; it is **not verified** that it can start from the V1 migration set. Two options, in order of preference. Owner: Given, choose, not done.

A. Rehearse on a restored copy of the real target (best, covers real data and sizes):

1. Take a backup of the target: `pg_dump -Fc -f before-v1.1.dump <database>` (store off the database host). Owner: Given, not done.
2. Restore into a scratch database on a separate server or a separate database name, never the live one: `createdb figbloom_v11_rehearsal` then `pg_restore --no-owner -d figbloom_v11_rehearsal before-v1.1.dump`. Owner: Given, not done.
3. Record before-numbers on the scratch copy: row counts of leads, contacts, companies, deals, activities, tasks, payments, members, organisations; the output of `npx prisma migrate status`. Owner: Given, not done.
4. Set `DATABASE_URL` (owner connection) and `APP_DATABASE_URL`, `PLATFORM_DATABASE_URL`, `PLATFORM_DB_PASSWORD` to the scratch database and run, in this order (from `docs/RUNBOOKS.md` section 3 and `docs/DEPLOYMENT.md`):
   - `npm run migrate:deploy` (on Neon, `npm run migrate:deploy:direct` with the direct, non-pooled URL; `DECISIONS.md` 7.3). Time it and note any migration that takes more than a few seconds. Owner: Given, not done.
   - `npm run db:bootstrap-role` then `npm run db:grant-role` (this release adds the platform role: `PLATFORM_DB_PASSWORD` must be set first).
   - `npm run seed` (production-safe catalogue reconcile; adds V1.1 permissions such as `mail.use` and `meetings.schedule`).
   - `npx tsx scripts/backfill-organization-defaults.ts`. Run it twice; the second run must add nothing.
5. While step 4's migrations run, probe a lead and a deal write every 25 ms (the rehearsal does this; a small script or the rehearsal's probe can be reused). Record the longest wait. Owner: Given, not done.
6. Check after: every before-number unchanged for tenant data; `npx prisma migrate status` clean; every table with an `organization_id` has row-level security and a policy (the rehearsal's check, reused; for the new platform tables see `20261105110000_platform_tables_tenant_isolation_policy` and `20261118090000_two_step_tables_rls`); read leads, contacts and deals through the app's own database role (not the owner); sign in as Management and as Sales on the scratch copy and open Leads, Deals, a quote, Forecast. Owner: Given, not done.
7. Rollback rehearsal: restore the same dump over the upgraded scratch copy; counts and migration list must equal the before-numbers. Record the time. Owner: Given, not done.
8. Record results in `docs/CUTOVER_PLAN.md` style or a new "Rehearsal results" section; do not leave them only in a terminal. Owner: Given, not done.

B. Scratch rehearsal on invented data (as on 26 Oct and 4 Nov for V1): adapt `scripts/migration-rehearsal.ts` to start from the V1 release tag and end at the release commit. Whether the script supports this is not verified. Owner: Given, not done.

## 5. Feature-flag rollout plan (per organisation)

How flags work (from `src/lib/featureFlags.ts` and `docs/FEATURE_FLAGS.md`):

- Release flags `release.v1`, `release.v11`, `release.v2`: on when the organisation's active release is at least that one. The deployment's release is `ACTIVE_RELEASE` (`v1`, `v1.1`, `v2`; unset means `v1`). An organisation can have its own release override (`setOrganizationRelease`, audited as `release_override.changed`); it is not an HTTP route (`docs/FEATURE_FLAGS.md`), so the platform console UI path is not verified here.
- Toggles (organisation settings, saved under `feature_toggles`, changed by Management with `PATCH /api/orgs/<org>/features`, audited as `feature_toggle.changed`). A toggle counts only when the release has reached its `minRelease`.

| Toggle | First release | Default | Controls |
|---|---|---|---|
| `quotes.enabled` | V1.1 | on | Quotes, approvals, forecast |
| `communication.group` | V1.1 | on | Chat, Mail, Meetings |
| `organisation.switcher` | V1.1 | on | Multi-organisation switcher |
| `assistant.enabled` | V1.1 | **off** | Ask Figbloom assistant |
| `preferences.own_colours` | V1.1 | on | Own colours |
| `integrations.enabled` | V1 | on | Click-to-chat and website capture |

Not flags: two-step sign-in, sequences, web forms, saved views, card capture and the mail and calendar connections have no toggle in `TOGGLES`; they are available once the release reaches V1.1 (and, for connections, once OAuth is configured). Whether any of them can be hidden per organisation is not verified. If staged exposure of these is wanted, a toggle must be added first (`docs/FEATURE_FLAGS.md`, "Adding a feature flag"). Owner: Given, decide, not done.

Important: a deployment with `ACTIVE_RELEASE=v1` keeps V1.1 off for every organisation that has no override. Raising `ACTIVE_RELEASE` to `v1.1` turns V1.1 on for every organisation at once. To roll out per organisation, keep `ACTIVE_RELEASE=v1` and override the release for chosen organisations, or raise the deployment and rely on toggles to hold features back (only the toggles above are available). Which of the two is chosen: Owner: Given, not done.

Proposed order (a proposal, not an agreement):

| Wave | Who | What | Exit before the next wave | Owner |
|---|---|---|---|---|
| 0 | Test organisation (invented data) | Release V1.1, all toggles on including `assistant.enabled`; run `docs/UAT_V1_1.md` | UAT done, no Blocker or Major open | Owner: Given, not done |
| 1 | The Figbloom organisation (Given, Michael) | V1.1 on; `assistant.enabled` off | Smoke checklist green; 2 working days with no Sev-1 or Sev-2 | Owner: Given, not done |

Any organisation can be moved back by turning the toggle off or removing its release override; both are audited. This hides the feature but does not undo data created while it was on.

## 10. Rollback

Authority: `docs/RUNBOOKS.md` section 2 (image rollback, database rollback, decision rule 2c). Summary, with V1.1 specifics:

1. **Feature rollback first (fast, no data loss):** turn the organisation's toggle off or remove its release override (section 5); or set `ACTIVE_RELEASE=v1` if no organisation needs V1.1. Data created while V1.1 was on stays in the database.
2. **Application rollback (usually safe):** redeploy the previous image or Vercel deployment noted in section 7 step 1. Migrations are additive in the main but do change shared things (the permission catalogue, removal of Customer Support in migration 29), so whether the previous version runs against the V1.1 schema is not verified: the rehearsal step "V1 code works on the upgraded database" (done for V0 to V1 on 4 Nov) must be repeated for V1 code on the V1.1 schema in section 4. Owner: Given, not done.
3. **Database rollback (slow, loses everything written since the backup):** stop the app; restore `before-v1.1.dump` into an empty database (`pg_restore --no-owner -d <database> before-v1.1.dump`); start the previous version. Migrations only go forward; the backup is the way back. Decision for Given, not for on-call.
4. A migration that fails half way: stop; do not re-run blindly; check `_prisma_migrations`; the Prisma `migrate resolve` command is a decision for Given (`RUNBOOKS.md` section 3).
5. Quotes already sent: share links already in customers' hands keep pointing at the app; after a rollback they may not resolve. Decide how to tell the customer. Owner: Given, not done.
6. Mail and calendar connections hold encrypted tokens; rotating `INTEGRATION_ENCRYPTION_KEY` invalidates them (people must reconnect). Do not rotate it during a rollback unless a leak is suspected.
7. Record the rollback in the daily log and the retrospective.
